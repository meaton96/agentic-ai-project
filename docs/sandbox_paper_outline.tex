\subsection{Agentic Systems}
\scaffold{Define an agent per NIST's definition (software that interacts
with its environment, receives information, undertakes self-directed
action toward an externally-specified goal). An agent = a model + a set of
tools + a loop that runs until something decides to stop. Note the pairing
this whole paper depends on: the generative power of a probabilistic LLM
paired with the logical certainty of a symbolic harness (domain rules,
hard constraints, human-operator validation or guards) -- research
consistently shows that choosing the model is not enough; orchestration
harness, memory strategy, context handling, validation path, and
checkpointing design drive practical agent behavior. \todo{Reuse Fig.~2
from the vision PDF (agent/environment interface diagram) or redraw it.}}

\subsection{Multi-Agent Systems}
\scaffold{When multiple agents coordinate or compete in a shared
environment toward complex shared objectives, they form an agentic
\emph{system}. Distinguish orchestrated MAS from peer-to-peer
agent-to-agent (A2A) negotiation -- both appear later as design points in
\S\ref{sec:casestudies}, not as a binary choice but as two ends of a
spectrum this paper's case studies sit at.}

\subsection{Manufacturing as the Driving Domain}

\subsection{Goals}
\label{sec:goals}
\scaffold{Reproduce and expand vision-paper \S2.1's four goals -- these are
the paper's thesis statements, not just a proposal's goals list:}
\begin{description}
  \item[Goal 1 -- BYOA] Every partner can deploy proprietary agents and
  multi-agentic workflows to experiment against other agents already in
  the Sandbox.
  \item[Goal 2 -- Holistic evaluation] What-if analysis and architecture
  trade-off evaluation for specific MAS workflows, so partners understand
  emergent system behavior and identify risk before deployment.
  \item[Goal 3 -- Translation avenue] University-based AI research results,
  implemented as specialized agents and workflows, get a path to industry
  adoption via an \emph{agentic marketplace} rather than the traditional
  one-off tech-transfer/licensing pipeline.
  \item[Goal 4 -- RIT value-add] Cyber risk assessment/mitigation,
  explainable agency, and safe-AI-in-MAS-context as capabilities RIT
  specifically contributes.
\end{description}

\subsection{Sandbox Design}
\label{sec:design}
\scaffold{Reproduce vision-paper \S2.2's three foundations, each expanded

\begin{itemize}
  \item \textbf{Partners} -- university, industry, and government entities,
  each a team of humans \emph{and} agents, potentially operating under

\section{Sandbox Infrastructure}
\label{sec:infra}
% ----------------------------------------------------------------------------
\scaffold{This section is new relative to the vision PDF -- it is the
technical-foundation section a paper needs that a funding pitch doesn't:
\emph{how does the Sandbox actually work, today, as code}. Draw from
\texttt{agent-sandbox/} (M0 schemas, M1 headless runtime) and vision-PDF
\S5. Be precise throughout about built-vs-proposed; see
\S\ref{sec:status}.}

\subsection{Schema-First Foundation: AgentSpec and RunSpec}
\scaffold{Every capability an agent can reach is registered through one
interface (MCP); every action is a typed, replayable event; every run is a
declarative spec rather than bespoke orchestration code -- the same
schema-first approach as Meta's Agents Research Environments (ARE),
independently converged on. An \texttt{AgentSpec} declares an agent's model
configuration, bound MCP servers, and any sub-agents it may delegate to; a
\texttt{RunSpec} declares a task against one or more AgentSpecs. Because
tools/model/sub-agent bindings are \emph{data}, not code, a partner's
proprietary agent can replace a seed agent by swapping one binding --
this is the concrete mechanism behind \texttt{SWAP\_AGENT} /
\texttt{ALTER\_MODEL} from \S\ref{sec:design}.}

\subsection{MCP-Mediated Tool Surface and Access Control}
\scaffold{Agents never call tools directly; every capability is exposed
through an MCP server binding with an explicit allowlist enforced before a
call reaches the server. Credentials resolve through a dedicated
credential layer -- a reference-only handoff that keeps raw secrets out of
an agent's context entirely. This is the concrete mechanism proposed to
extend MCP with institution-specific, policy-driven access control
(\S\ref{sec:merit}).}

\subsection{Observability: the Event Log}
\scaffold{Every model call, tool call, and sub-agent spawn is written to
an append-only, per-run typed event log, with a configurable redaction
policy (full / hashed / metadata-only) applied per binding before
persistence. This is the substrate for explainable agency (Goal 4,
\S\ref{sec:goals}): because every agent's actions are captured uniformly
regardless of model or tools used, a partner can audit or replay a run,
including across agents using different LLMs.}

\subsection{Isolation Boundary}
\scaffold{Every MCP server registered in the Sandbox's agent store is
local to the Sandbox; by default, no agent has outbound access to
external networks, databases, or unregistered MCP servers. This is what
makes the Sandbox a genuine ``safe space'' structurally, not just by
policy convention -- enforced at the same boundary that mediates every
tool call, not left to an agent's good behavior or a partner's
configuration.}

\subsection{Implementation Status}
\label{sec:status}
\scaffold{State this plainly and specifically -- this is a paper section,
not a proposal, so ``future work'' claims need to be honestly separated
from ``already works, here's the evidence.'' \todo{Verify current state

\begin{itemize}
  \item \textbf{Built and tested:} a schema layer (agent/run/event
  specifications, pydantic v2) and a headless single-agent runtime --

\end{itemize}

system \emph{is} the Sandbox.}

\subsection{Case Study I: Multi-Agentic Predictive Maintenance}
\label{sec:casestudy1}
\scaffold{Summarize, don't re-derive: six specialized agents (intake,
feature engineering, profiler, modeling, verification, deep-dive) under a
deterministic harness holding exclusive authority over splitting,
metrics, leakage detection, and sandboxed execution. Every agent output is
a JSON proposal the harness independently re-validates. A dynamic
orchestrator variant replaces the fixed six-step sequence with a
nine-entry agent catalog and a planning agent, itself subject to the same
propose-then-verify discipline applied to control flow.}
\begin{itemize}
  \item \textbf{Validated on:} NGAFID aviation predictive-maintenance data
  (22 sensor channels, \textasciitilde1\,Hz, 4.2\,GB source, streaming
  bounded-memory featurization, entity-aware splitting by aircraft), plus
  Titanic/Iris for binary/multiclass generalization.
  \item \textbf{Relevant finding for this paper specifically:} real-LLM
  evaluation (not just hermetic stubbed-client tests) surfaced two genuine
  findings a purely architectural description wouldn't -- (1) the dynamic
  orchestrator matched or exceeded the fixed baseline (e.g., autonomously
  retrying a modeling step past a hardcoded candidate budget the baseline
  couldn't get past), and (2) the harness's state bookkeeping held under
  adversarial pressure (a prompt-injection string embedded in training
  data could not make the system assert a model was finalized unless
  finalization genuinely executed).
  \item \textbf{What this validates about the Sandbox pattern:} a
  MAS can give agents genuine judgment authority (target selection,
  feature proposals, template choice, even control-flow sequencing) while
  a non-agentic layer retains sole authority over everything
  correctness-critical -- the same authority split \S\ref{sec:infra}
  proposes at the infrastructure level (MCP allowlists, isolation
  boundary) is shown here to work at the application level too.
\end{itemize}

\subsection{Case Study II: Direct Agent-to-Agent Resource Scheduling}
\label{sec:casestudy2}
\scaffold{Summarize the resource-scheduler (6G-enabled factory-floor
scheduling, six agents: load monitor, task prioritization, resource
allocation, failure recovery, optimization, human oversight). Key
architectural contrast with Case Study I: this system deliberately tests
\emph{direct} agent-to-agent (A2A) messaging for the negotiation-shaped
parts of the workflow (task prioritization $\to$ resource allocation,
failure recovery $\to$ resource allocation), instead of routing everything
through a central orchestrator -- while still keeping a deterministic
environment/state layer as the sole source of truth for machine/slice
state and constraint arithmetic. Every A2A send is still logged as an
event; ``direct'' does not mean ``unaudited.''}
\begin{itemize}
  \item \textbf{What this validates:} the propose/decide trust-boundary
  pattern is not tied to one specific orchestration topology --
  it holds whether agents communicate through a central orchestrator
  (Case Study I) or negotiate peer-to-peer with a deterministic gate on
  receipt (Case Study II). This is directly relevant to the Sandbox's
  BYOA goal: partners' agents may not share one communication topology,
  and the Sandbox's trust model needs to accommodate both.
  \item \textbf{Status/scope caveat:} \todo{state current implementation
  maturity honestly -- per repo state as of this outline, all six agents
  are individually scaffolded and testable, but there is no orchestrator
  tying all six into one run yet, and no live-model evaluation comparable
  to Case Study I's. Decide before drafting whether this is presented as
  full evaluation evidence or as a preliminary/architectural data point --
  see open item in \texttt{docs/paper\_outline.md}.}
\end{itemize}

\subsection{What the Case Studies Show, Together}
\scaffold{Close the section by pulling the thread back to the Sandbox
explicitly: two independently-built systems, different domains, different
orchestration topologies, arrived at the same authority split. That's the
argument for why a shared Sandbox infrastructure (rather than each partner

\section{Intellectual Merit}
\label{sec:merit}
% ----------------------------------------------------------------------------
\scaffold{Reproduce and expand vision-paper \S4's five bullets as
subsections -- these double as the paper's forward-looking research
agenda and (if this becomes a journal/longer submission) as material for
a dedicated Related Work + Future Work split.}

\subsection{Enhanced MCP Architecture}
\scaffold{MCP standardizes tool/data access but doesn't itself address
multi-institutional data governance. Proposed extensions: (1) secure
access to off-site/distributed data stores, (2) institution-specific
policy-driven access control, (3) mechanisms to detect/prevent unintended
data leakage across agents, tools, and institutional boundaries.}

\subsection{Multi-Agent Harness Engineering}
\scaffold{Harnesses mediate LLM$\leftrightarrow$tool/data/environment
interaction to improve reliability, but harness engineering today is
largely manual and requires deep domain expertise. In MAS specifically,
an erroneous output from one agent can propagate to downstream agents,
causing cascading failures. Research direction: automated, domain-aware
harness engineering for MAS -- constraining agent actions, monitoring
inter-agent interactions, detecting erroneous behavior, and mitigating
error propagation across the workflow.}

\subsection{Emergent Cybersecurity Challenges in MAS}
\scaffold{MAS execute multi-step workflows, retain persistent state, and
hold active credentials -- expanding the attack surface beyond
conventional software vulnerabilities to include manipulation of
reasoning processes, exploitation of inter-agent communication protocols,
and unauthorized/unintended tool invocation. Existing cybersecurity
frameworks, built for static human-directed software, don't adequately
address this. \todo{Note explicitly: this is proposed research, not yet
evaluated in this paper -- the adversarial prompt-injection result in
\S\ref{sec:casestudy1} is a narrow, single-property test (state-bookkeeping
integrity), not a general MAS security evaluation. Don't conflate the
two.}}

\subsection{System-Level Innovation in MAS}
\scaffold{Even a modest set of agents admits an astronomically large space
of possible configurations/architectures -- one that grows far faster
than the capacity to evaluate it, and exhibits emergent behaviors
(feedback loops, bottlenecks, critical thresholds, phase transitions)
that can't be inferred from individual agents' designs. Draws on systems-
thinking literature for rigorous system-level performance analysis,
what-if evaluation, and optimization -- this is Goal 2 (\S\ref{sec:goals})
made into a research problem, not just a platform feature.}

\subsection{University-Industry Collaboration as an Innovation Lab}
\scaffold{The traditional tech-transfer/licensing model requires upfront
agreement on deliverables, IP sharing, and timelines before research
happens -- often the actual blocker to collaboration, not a shortage of
good ideas. The Sandbox's agentic-marketplace model instead lets
collaboration happen through experimentation itself: partners showcase AI
innovations as agents, connecting 2-sided or multi-sided based on
complementary needs and competencies discovered \emph{during} use, not
negotiated in advance.}

\section{Limitations and Future Work}
